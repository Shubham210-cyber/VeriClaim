# DECISIONS (authoritative addendum)

Where this file conflicts with any other doc, **this file wins**. These
resolve the conflicts/gaps found in the plan review. Product name in docs is
"ClaimProof"; the GitHub repo is "VeriClaim" (same project).

## Scope and time
- **Hard 3-hour build.** The old 48-hour phase table is replaced (see
  IMPLEMENTATION_PHASES.md). Customer upload link is in scope but built last.
- Dev runs on localhost only. **No reviewer auth** (demo). Bind backend to
  127.0.0.1; say so in README. `GET /health` stays unprefixed.

## Evidence / extraction
- PNG/JPEG/PDF/TXT supported. **Images are OCR'd with Tesseract** behind an
  `OcrEngine` adapter (path from `TESSERACT_CMD` env or default Windows
  install path). If Tesseract is missing -> `ExtractionStatus.FAILED`
  with code `OCR_UNAVAILABLE` (never a rejection).
- Demo evidence = generated images/PDFs/TXT that visibly say
  **"FAKE - SYNTHETIC DEMO DOCUMENT"**. Generated by `scripts/make_fixtures.py`.
- Extraction is deterministic (regex over labelled lines, e.g. `Purchase Date:`).
  **AI is NOT used for extraction in the MVP**, only for summaries.
- Regex confidence: digital PDF/TXT label match = 0.95; OCR = mean Tesseract
  word confidence/100 clamped to <=0.90; threshold 0.80 (`CONFIDENCE_THRESHOLD`).
- Dates: accept ISO `YYYY-MM-DD` and `DD Mon YYYY`/`DD-Mon-YYYY`.
  Numeric `DD/MM/YYYY` where both parts <=12 is **ambiguous -> fact kept raw,
  normalized_value null, rule INDETERMINATE**. Purchase-date mismatch
  tolerance = 0 days (exact).

## Facts
- `field_name` vocabulary (enum `FieldName`): `product_model`,
  `device_identifier`, `purchase_date`, `incident_date`, `repair_date`,
  `purchase_amount`, `repair_amount`, `currency`, `event_description`,
  `policy_id`.
- Claim-entered values become facts with `source = CLAIM_RECORD`,
  `evidence_id = null`, `extraction_method = MANUAL`. Document-derived facts
  have `source = DOCUMENT` and a required `evidence_id`.
- "Latest" fact per field = from the highest `version_number` evidence of each
  evidence_type; ties by newest `uploaded_at`. Older versions are kept.
- `version_number` = count of prior evidence of the same `evidence_type` on
  that claim + 1.

## Event classification
- Claim has a reviewer-selected **`event_type`** (enum `EventType`:
  `MANUFACTURING_DEFECT`, `HARDWARE_FAILURE`, `ACCIDENTAL_DAMAGE`,
  `LIQUID_DAMAGE`, `THEFT`, `COSMETIC_WEAR`, `OTHER`). Required for rules
  POL-005/006; if `OTHER`/missing -> INDETERMINATE.
- A keyword helper may *suggest* an event_type from the description in the UI
  only; it never feeds a rule on its own.

## Policy
- Policy key is `id` + `policy_version`; MVP seeds version `1` only.
  Evaluation stores `policy_id` and `policy_version`.
- Extra policy fields: `requires_incident_description` (bool),
  `requires_repair_receipt_if_repaired` (bool), `cap_is_eligibility_ceiling`
  (bool, default false).
- `required_evidence_types` lists only uploadable types (never POLICY_DOCUMENT;
  policy comes from the seeded catalogue).
- Claim has `repair_already_performed` (bool, default false) which triggers
  EV-003 when the policy requires it.
- New rules: `EV-005_REQUIRED_INCIDENT_INFO` (incident date + description
  present), `CON-009_CURRENCY_MISMATCH`.
- Amounts: deductible applied **after** cap: `min(claimed, cap) - deductible`,
  floor 0, shown as INFO "estimate". Cap exceeded -> `FAIL/MEDIUM` unless
  `cap_is_eligibility_ceiling` (then HIGH, rejection candidate).

## Recommendation precedence (final)
1. PROCESSING_FAILED (critical technical failure / policy missing)
2. HUMAN_REVIEW_REQUIRED (any FAIL of severity >= HIGH in `CON-*`, i.e. a
   material conflict; or ambiguous classification)
3. **RECOMMENDED_REJECTION** if a POL rejection-candidate FAIL
   (`POL-006`, hard `POL-001/002/003/004`, ceiling cap) exists whose facts are
   reliable **and** not affected by any conflict -- this now outranks plain
   missing evidence (exclusion doesn't depend on the invoice), but only for
   POL-005/006/001/002/004. `POL-003` (window) needs purchase_date, so it
   requires that evidence present.
4. MORE_INFORMATION_REQUIRED (missing/unreadable/INDETERMINATE required items)
5. RECOMMENDED_APPROVAL (all required PASS, no FAIL/INDETERMINATE)
6. Else HUMAN_REVIEW_REQUIRED.
Demo CP-DEMO-004 is fixed at **HUMAN_REVIEW_REQUIRED**.

## Statuses
- Evaluation is synchronous. `PROCESSING` only set transiently; on exception
  claim -> `PROCESSING_FAILED` with an audit event.
- After evaluation: claim -> `AWAITING_REVIEW` (or `PROCESSING_FAILED`).
- Decision -> claim status: APPROVE->APPROVED, REJECT->REJECTED,
  REQUEST_INFORMATION->AWAITING_CUSTOMER, ESCALATE->ESCALATED,
  MARK_UNDER_REVIEW->AWAITING_REVIEW. APPROVED/REJECTED are terminal for
  decisions except ESCALATE; further decisions on them -> 400. `CLOSED` unused.
- Decision must reference the **latest** evaluation (else 409
  `STALE_EVALUATION`). `is_override` is stored = action does not match the
  recommendation (APPROVE vs RECOMMENDED_APPROVAL, REJECT vs
  RECOMMENDED_REJECTION, REQUEST_INFORMATION vs MORE_INFORMATION_REQUIRED,
  ESCALATE vs HUMAN_REVIEW_REQUIRED). Reason required if REJECT or override.
- `REQUEST_INFORMATION` decision creates the upload request itself (body may
  include `expires_in_hours` default 72 and `max_uploads` default 5). The
  separate `/upload-requests` endpoint is kept only for revoke
  (`POST .../upload-requests/{id}/revoke`).

## Customer upload
- Token goes in header **`X-Upload-Token`** on `/api/v1/public/upload-request`
  (GET) and `/api/v1/public/upload-request/evidence` (POST). The customer page
  URL (`/customer-upload/<token>`) is frontend-only, so API access logs never
  hold the token. Backend access log for `/public/` is not enabled.
- `max_uploads` counts accepted files. Customer may only upload evidence
  types listed in the request's requested items (+ `OTHER`).
- Upload by customer auto-appends evidence, sets claim `AWAITING_REVIEW`, and
  **re-evaluates** (new Evaluation). Response to customer is minimal.
- Simple in-memory rate limit on failed token lookups per IP.

## Duplicate hash (CON-007)
- Flag only (INFO/LOW -> review note, never blocks) when the same sha256
  appears on another claim, or twice in one claim under *different*
  evidence types. Re-upload of same file as new version of same type: ignored.
- Fixtures are unique per claim.

## Persistence tech
- SQLAlchemy 2.x (no SQLModel). SQLite with `PRAGMA foreign_keys=ON`.
- Money stored as **TEXT** (Decimal str). Datetimes stored UTC.
- `create_all` at startup; idempotent seed.
- Audit append-only enforced in code (no update/delete function exists).

## AI
- Interface: `AiProvider.summarize_findings(claim, facts, findings) -> AiSummary`.
  No extraction method in MVP.
- `mock` = deterministic template text (default). `sonnet` = Anthropic API via
  `ANTHROPIC_API_KEY`, model from `AI_MODEL` (default `claude-sonnet-5-5`).
- Evaluation.`ai_provider` in {`mock`,`sonnet`,`none`}; failures -> template
  summary + `SYS-002_AI_UNAVAILABLE` INFO finding.

## Claims list
- `GET /claims` adds `submitted_from`, `submitted_to` (ISO dates).
- Claim numbers: `CP-YYYY-NNNN`; demo seeds use `CP-DEMO-00N`.
- Claim POST additionally accepts `event_type` and `repair_already_performed`.

## OCR and extraction v2 (real-world invoices)
- OCR preprocessing: grayscale, upscale to ~2400px wide, autocontrast, sharpen; Tesseract runs in two layout
  modes (psm 6 and psm 4) and the lines are merged (better variant first). Per-line confidence = median word
  confidence, capped at 0.90.
- Parsers match values by shape (date / identifier / money) with the label anywhere on the line, so merged
  two-column lines work. Dates accept `30.03.2018`; ambiguous numeric dates are still never guessed.
- Amount: last money value on the labelled line; else the spelled-out "Amount in Words" total
  (`words_to_number`, refuses unknown words). When both exist and agree, confidence is boosted; when they
  disagree, confidence is forced to 0.5 (verification).
- Product model: explicit label, else the claimed model located literally in the text (a verification, quotes
  the document), else the invoice line-item table guess capped at 0.75 (< 0.80 threshold, so it never accuses).
  CON-001 says INDETERMINATE (MODEL_NOT_FOUND) if a readable invoice never shows the claimed model.
- CON-008 only considers fields rules actually use (purchase_amount is informational, excluded).
- Limit: OCR can misread the rupee symbol/separators; amounts are only used by CON-006 (repair receipts).

## Product naming (UI)
- UI brand is **VeriClaim**. Users never see policy IDs, rule IDs or enum names. Policies show friendly names
  (e.g. "Laptop Manufacturer Warranty (12 months)"); rule IDs are behind a "Technical details" toggle.
- API still uses stable IDs; `policy_name` is added to claim responses.
